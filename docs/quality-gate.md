# Единый quality gate

Quality gate является единой точкой решения: допустим ли текущий срез проекта
к сборке релизного артефакта.

## Локальная проверка

```bash
npm run check
```

Последовательно и с остановкой на первой ошибке выполняются:

1. границы модулей и поиск циклических зависимостей;
2. единый контракт подготовки состояния всех E2E-сценариев;
3. статический анализ;
4. unit- и integration-тесты;
5. factual eval ИИ-тренера;
6. production-сборка со строгой проверкой TypeScript;
7. проверка целостности PWA-артефакта;
8. контроль размера начальных JS/CSS, движка и всего production-артефакта.

## Полная релизная проверка

После однократной установки браузера:

```bash
npm run test:e2e:install
npm run check:ci
```

Команда добавляет одиннадцать браузерных барьеров. Все они запускаются против уже
проверенного production preview, поэтому проходят тот же код, который попадает
в артефакт:

1. критический сценарий «партия → разбор → тренировка»;
2. accessibility smoke по WCAG 2.1 AA для главного экрана и панели импорта;
3. offline-E2E с установкой service worker, проверкой precache и повторным
   запуском приложения при отключённой сети.
4. визуальная регрессия основного экрана при фиксированных desktop- и
   mobile-размерах, включая защиту от горизонтального переполнения.
5. клавиатурная навигация: skip-link, управление вкладками стрелками,
   `Home`/`End`, открытие сворачиваемых панелей и возврат фокуса.
6. Core Web Vitals: LCP, CLS и INP на production-сборке в Chromium.
7. восстановление после повреждения локальных настроек и JSON-данных с
   сохранением исправных записей и данных других приложений.
8. миграция данных из `localStorage` в IndexedDB, повторный запуск из новой
   базы и fallback при недоступной IndexedDB;
9. WebKit-проверка критического учебного цикла и клавиатурного сценария как
   автоматический барьер совместимости с Safari.
10. интервальное повторение слабых тем с восстановлением сохранённой очереди;
11. первый запуск, выбор цели и переход в диагностическую партию.

Отдельный диагностический запуск:

```bash
npm run test:e2e:smoke
npm run test:e2e:a11y
npm run test:e2e:offline
npm run test:e2e:visual
npm run test:e2e:keyboard
npm run test:e2e:performance
npm run test:e2e:recovery
npm run test:e2e:migration
npm run test:e2e:webkit
```

## Отчёт

Каждый запуск создаёт `quality-gate-report.json` со статусом, версиями среды и
длительностью этапов. Размеры production-файлов записываются в
`performance-budget-report.json`, измеренные браузерные метрики — в
`web-vitals-report.json`. Файлы не попадают в Git. CI сохраняет их вместе с
production-сборкой при успехе либо с Playwright-диагностикой при падении.

Лимиты хранятся в `performance-budget.json`. Начальный JavaScript ограничен
500 000 байт без сжатия и 150 000 байт gzip, начальный CSS — 90 000 и 18 000
байт соответственно. Начальный документ с подключёнными ресурсами не должен
превышить 600 000 байт, WebAssembly движка — 8 000 000 байт, весь `dist` —
9 000 000 байт. Core Web Vitals используют границы good: LCP ≤ 2500 мс,
CLS ≤ 0,1 и INP ≤ 200 мс.

Accessibility-порог не допускает нарушений правил WCAG 2.0/2.1 уровней A и AA
в проверяемых состояниях. Offline-порог требует активный service worker, ровно
один актуальный кеш сборки, закешированные HTML/JS/CSS и успешную загрузку
интерфейса без сети.

Визуальный порог сравнивает интерфейс с эталонами Linux Chromium при размерах
1440×1000 и 412×915. Шрифт Inter поставляется вместе с приложением, поэтому
метрики текста не зависят от набора системных шрифтов. Намеренное изменение
интерфейса фиксируется только после ручной проверки обоих новых изображений:

```bash
npm run test:e2e:visual:update
```

WebKit запускается с профилем `Desktop Safari`. Это не заменяет ручную проверку
на реальном iPhone, но блокирует релиз при несовместимости DOM, событий,
фокуса и основного учебного сценария с движком Safari.

Изменение релизных порогов, отключение этапа или разрешение падения требует
отдельного архитектурного решения. Зелёный результат одной проверки не заменяет
общий gate.
